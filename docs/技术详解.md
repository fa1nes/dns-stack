# dns-stack 技术详解：两台机器上的抗污染递归解析

## 摘要

dns-stack 是给自己家用的 DNS 递归解析器：家里的手机、电脑通过加密的 DoH / DoT 把查询发给它，它从根服务器开始一级级问下去，把答案交回设备。

它不是托管型的权威 DNS 平台。权威平台替别人的域名回答「这个名字是什么地址」；dns-stack 替自己的设备去问全世界。所以它关心的问题也不一样：

* **拿到没被污染的答案**：境外域名的查询经隧道从香港出网，墙看不见查询本身，自然也无从伪造应答。
* **拿到离自己最近的节点**：国内域名直连国内权威，并把设备所在的 /24 网段（ECS）带给 CDN，让它按真实位置调度。
* **出了故障能自己恢复、恢复不了也看得见**：降级、自愈、限流都尽量自动，自动不了的要在面板上一眼看到。

整套系统只有两台机器：一台国内服务器承担全部功能，一台香港服务器只负责让境外查询从境外出网。

## 核心架构：四层分工

```
                    设备（DoH / DoH3 / DoT / DoQ）
                              │
  ┌─────────────── 国内节点 cn-resolver ───────────────────────────┐
  │ 入口层   mosproxy：加密入口、缓存、黑名单、访问控制、限流     │
  │              │                        │（降级 / 指定域名）    │
  │ 递归层   本机 Unbound :5335 ──────────┼─────────────┐         │
  │              │ 每一跳问权威，按权威 IP 分流            │         │
  │          ┌───┴──────────────┐                         │         │
  │      权威在大陆          权威在境外                    │         │
  │       直连出网        打标 → WireGuard 隧道            │         │
  │                                                         │         │
  │ 数据层   分流数据流水线：大陆网段、国内权威、ECS 白名单、分片表 │
  │ 运维层   采集器 · 面板 · 特权助手 · 看门狗 · 例行维护             │
  └─────────────────────────────┬──────────────────────────┼─────────┘
                                │ wg0 10.100.0.2 ⇄ 10.100.0.3
  ┌──────── 香港节点 offshore ──┴──────────────────────────┴─────────┐
  │ WireGuard 出口 + 香港 Unbound :5335（mosproxy 的降级上游）         │
  └────────────────────────────────────────────────────────────────────┘
```

### 入口层：mosproxy

* 监听 DoH（443/TCP）、DoH3（443/UDP）、DoT（853/TCP）、DoQ（853/UDP）。
* 64MB 乐观缓存：过期的答案先回给设备，后台再去刷新，热门域名几乎从不让设备等递归。
* 域名黑名单命中直接回 NXDOMAIN，连递归都不发生；访问控制（nftables）只放行授权网段访问加密端口。
* 限流：并发 500、每秒 2000 次查询，挡住单个失控客户端。
* 上游是一个按顺序降级的负载均衡：先本机 Unbound，它不应答就转香港 Unbound。

### 递归层：本机 Unbound + 出口分流

Unbound 自己从根区完整递归，不依赖任何公共 DNS。关键在**它发出去的每一个包走哪条路**：nftables 匹配 Unbound 进程发出的流量，目标是大陆地址（`@direct4`）或已知的国内权威（`@cn_authority`）就直连，否则打上标记、走隧道到香港出网。隧道断了，打标的包被策略路由显式拒绝——宁可解析失败，也不回落直连拿污染答案。

判据是「这台权威服务器在哪」这个可核验的网络事实，而不是「这个域名算不算国内的」这种要人工维护的分类。详见 README「工作剖析」。

### 数据层：分流数据流水线

一个每 15 分钟运行一次的 Go 流水线，产出分流所需的全部数据：

| 产物 | 规模（2026-10-01） | 用途 |
|---|---|---|
| `direct4`：大陆 IPv4 网段 | 6,601 段 | 直连集合；源为 APNIC 委派记录，用 qqwry 补充并反向排除 |
| `cn_authority`：国内权威 | 186 段 | 权威含大陆地址的区域，境外地址严格按 /32 |
| ECS 白名单 | 6,881 条 | 哪些权威可以收到设备的子网 |
| ECS 分片表 | 8,411 行 | 大陆地址按「省份 + 运营商」切片，决定缓存按什么粒度区分子网 |
| 污染 IP | 58 个 | 墙伪造应答里出现过的地址，供对照排查 |

各步骤有自己的周期（归属库与大陆网段每天、共享 anycast 识别每小时、国内权威与 ECS 白名单每 15 分钟），按依赖顺序执行，上游失败时下游不拿旧数据硬算。

### 运维层

| 组件 | 职责 |
|---|---|
| 采集器 | 包着 mosproxy 运行，把查询日志写进 SQLite（保留 7 天）；采集出错时继续读空管道，绝不拖住 DNS |
| 管理面板 | 概览、查询明细、域名统计、诊断工具、设置；统计只读，只有删除单条记录时写库 |
| 特权助手 | 唯一能做 root 操作的进程，面板通过本地套接字调用，有固定白名单和角色闸门 |
| 分流看门狗 | 每分钟检查一次分流链路，异常时自动重建 |
| 例行维护 | 证书续签、备份、日志清理 |

## 一次解析的旅程

以手机查询一个境外 CDN 上的网站为例：

1. **加密到达**：手机经 DoH 把查询发到国内节点 443 端口，mosproxy 检查访问控制与黑名单。
2. **先看缓存**：缓存命中就立即返回（这是绝大多数情况，见下文负载画像）；已过期的条目也先返回、后台刷新。
3. **交给递归**：未命中则转给本机 Unbound。Unbound 从根开始，依次询问 `.com` 的权威、域名自己的权威、CNAME 指向的 CDN 权威。
4. **每一跳独立分流**：问根和 `.com` 权威时，目标多在境外，这几个包经隧道从香港出网；如果 CDN 的权威在大陆，这一跳就直连。一次解析里直连与隧道可以交替出现，判断只看那一跳的目标地址。
5. **带上位置**：CDN 权威在 ECS 白名单里，Unbound 就把手机所在的 /24 一起发过去，CDN 按手机的真实位置挑节点，而不是按隧道出口（香港）。
6. **按片缓存**：mosproxy 按 ECS 分片表把设备归到「省份 + 运营商」分片，答案按分片缓存，同一片里的其它设备直接复用。
7. **返回并记录**：答案经 mosproxy 返回手机；采集器记下域名、类型、走了哪条路、耗时，供面板统计。

如果第 3 步本机 Unbound 没有应答，mosproxy 会把查询转给香港 Unbound，由它从境外完整递归。这条降级路径拿不到国内 CDN 的就近节点，但能保证不中断。

## 关键能力

### 1. 出口分流：把污染变成结构上不可能

见上文递归层。有两点值得单独说明：

* **共享 anycast 不能聚合**：一些境外 CDN 的权威和国内服务共用 anycast 地址，按网段聚合会把它们误判成国内。所以境外权威只按 /32 精确收录，并有专门的步骤每小时识别这类地址。
* **判据缺席时不冒充健康**：归属库、大陆网段任一不可用时，相关步骤保留上一版产物、不写空结果；数据骤降超过阈值时拒绝下发。

### 2. ECS 就近：分流架构的必需品

境外 CDN 的权威在境外，查询必然走隧道。如果它收不到设备的子网，只能按香港出口判断位置，把国内用户调度到香港节点：链路通、解析成功，但绕了一大圈。所以 ECS 白名单按「这台权威服务谁」收敛：只要 CDN 直连规则集证明某家 CDN 在大陆有节点，它的境外权威就进白名单。

`dns-stack cdn-hit` 是这条链路的验收工具：以真实中国 /24 的身份解析各家大厂域名，报出「这家 CDN 在大陆有节点、答案却落在境外」的情况。

### 3. 健康检查、降级与自愈

| 故障 | 自动处理 | 在哪里看见 |
|---|---|---|
| 本机 Unbound 无应答 | mosproxy 转香港 Unbound | 面板侧栏状态点变红、概览横幅 |
| 香港 Unbound 离线 | mosproxy 健康检查剔除；香港侧 supervise-daemon 2 秒内拉起 | 状态点变黄、横幅列出「香港 Unbound 递归 离线」、上游表格、自检「上游全部在线」、告警推送 |
| 分流规则丢失（nft / 策略路由） | 看门狗每分钟检查，异常时重建，连续失败 5 次后停手等人工 | 自检、看门狗日志 |
| 隧道断开 | 打标流量被显式拒绝，境外解析失败但不回落直连 | 自检「香港递归可用」「境外域名解析」 |
| 某个批处理任务内存失控 | systemd 内存上限只杀掉这个任务，不连累解析 | 模块状态 |

**主动告警**：看门狗每分钟汇总一次异常（分流链路问题、mosproxy 无响应、离线的上游），只在异常出现、变化、恢复时各发一条消息，不会每分钟重复刷屏；发送失败会在下一分钟重试。在 `config.env` 里设置 `ALERT_WEBHOOK` 即可启用，消息以 JSON `{"title": …, "body": …}` POST 过去，可以直接填 Bark 的推送地址（`https://api.day.app/<你的 key>`）。不设置就不发送。

香港节点每月 1 号凌晨会按计划重启一次。Unbound 监听的隧道地址要等 wg0 起来才存在，所以它配置了 `ip-freebind`（启动顺序无关）并由 supervise-daemon 守护；这两项由 `install-hk.sh` 负责。

### 4. 访问控制与黑名单

| | 文件 | 生效方式 |
|---|---|---|
| 域名黑名单 | `blocklist.txt` | mosproxy 直接回 NXDOMAIN |
| 访问控制 | `acl.txt` | 渲染成 nftables 链，只放行列出的网段访问加密端口；空文件表示不启用 |

面板修改访问控制时有防自锁闸门：改完之后请求方自己不在授权网段里，就拒绝下发。

### 5. 查询观测

面板的数据都来自采集器写的 SQLite：实时查询流、近 24 小时趋势、域名排行、失败域名、各上游的成功率与延迟（平均值和按直方图插值的 p95）。统计窗口可以通过「重设统计起点」截断，所有「近 24 小时」的数字共用同一个起点。

量过才知道该优化什么。2026-10-01 的 7 天数据：

| 指标 | 数值 |
|---|---|
| 查询量 | 127,405 次（约 0.2 次/秒） |
| 缓存命中 | 91.1% |
| 国内递归 | 8.6% |
| 境外递归 | 0.02% |
| 解析失败 | 0.3% |

这是一个几乎全在境内访问的家庭网络。DNS 解析路径上不跑 Go 代码，Go 只负责数据生成、采集和管理，所以性能工作的重点是**批处理任务的峰值内存**（机器只有 1.8GB），而不是吞吐。

## 模块一览

国内节点（`ROLE=cn-resolver`）：

| 模块 | 类型 | 周期 |
|---|---|---|
| mosproxy（DNS 入口，同时承载采集器） | 常驻 | — |
| Unbound（递归解析器） | 常驻 | — |
| dns-stack-recursive-routing（出口分流） | 常驻 | — |
| wg-quick@wg0（香港隧道） | 常驻 | — |
| dns-stack-panel / dns-stack-helper | 常驻 | — |
| dns-stack-routing-watchdog（分流看门狗） | 定时 | 1 分钟 |
| dns-stack-routing-data（分流数据流水线） | 定时 | 15 分钟 |
| dns-stack-collect-polluted（污染 IP 采集） | 定时 | 6 小时 |
| dns-stack-maintenance（例行维护） | 定时 | 6 小时 |

香港节点（`ROLE=offshore`）只有 Unbound、wg-quick@wg0 和每日的日志瘦身。模块清单的唯一来源是 `internal/stack`，面板、助手、自检都从它派生。

## 演进方向

结合只有两台机器的现实，按价值排序：

* **境外查询改为转发给香港递归**：实测同一个冷缓存查询能快 37%–50%，但境外递归只占 0.02% 的查询，而且要改动最脆弱的 ECS 链路。负载画像不变的话不值得做。
* **IPv6**：分流集合目前只覆盖 IPv4。家里设备的 IPv6 流量多起来之后，`direct4` 需要对应的 IPv6 版本。
* **第二个境外出口**：香港是单点。只有当境外解析的可用性真的变得重要时，再考虑第二台机器做互备。

参考的托管型权威平台里，套餐计费、NS 托管、DDoS 清洗、HTTPDNS SDK 这些能力解决的是服务外部客户的问题，不适用于这套家用系统。HTTPDNS 想解决的「绕过运营商 Local DNS 劫持」，这里由 DoH 入口承担。
