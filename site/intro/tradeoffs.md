# 设计取舍

这一页记录「为什么是现在这个样子」，以及哪些看起来该做、量过之后决定不做的事。所有判断都基于实测，条件变了就该重新评估。

## 先看负载，再谈性能

截至 2026-10-01 的 7 天：

| 指标 | 数值 |
|---|---|
| 查询量 | 约 13.5 万次（约 0.2 次/秒） |
| mosproxy 缓存命中 | 90.1% |
| 国内递归 | 9.6%，平均 311 ms |
| 境外递归 | 0.03% |
| 解析失败 | 0.32% |

结论：

- **DNS 解析路径上不跑 Go 代码**。查询经 mosproxy 和 Unbound 处理，Go 只负责生成数据、采集和管理。优化 Go 代码不会让解析变快。
- 真正的约束是国内机器的 **1.8GB 内存**。每个批处理单元都设了 systemd `MemoryHigh` / `MemoryMax`；新的重计算先在 CI 或本机用真实数据量测峰值，再上生产。CI 里有一道 256MB 的规模闸门专门卡分流数据生成。
- 性能假设必须先量：曾经断言能快 5–20 倍的改动，实测只有 1.07 倍。

## 隧道断了宁可失败

境外查询在隧道断开时会**显式失败**，而不是回落直连。回落直连拿到的是被污染的答案：看着解析成功，实际更危险。这是用可用性换正确性，而且是有意的。

## 只做 IPv4 出口

分流集合 `direct4` 和 WireGuard 隧道都只有 IPv4。所以国内节点的 Unbound 配置 `do-ip6: no`：**不经 IPv6 向权威发查询**（AAAA 记录照常解析，那是数据，和传输协议无关）。

这一条有过教训。线上配置曾经是 `do-ip6: yes`，而国内机器根本没有 IPv6 路由。对 IPv6 地址很多的区域（例如 `pool.ntp.org` 有 30 多个 IPv6 权威地址），Unbound 会把每次查询的 32 次发送预算全部花在不可达的 IPv6 地址上，然后返回 SERVFAIL。7 天里全部解析失败的 43% 来自这一个原因。修复后自检多了一项「Unbound 运行配置与模板一致」，用来发现线上配置和仓库模板走散。

等家里设备的 IPv6 流量真的多起来，需要的是 `direct6` 和带 IPv6 的隧道，而不是简单打开 `do-ip6`。

## 量过之后决定不做的事

| 想法 | 实测 | 结论 |
|---|---|---|
| 境外查询改为转发给香港递归，而不是本机递归 + 隧道 | 冷缓存下快 37%–50% | 受益的只有 0.03% 的查询，而且要改动最脆弱的 ECS 链路。不做 |
| 第二个境外出口做互备 | 香港是单点，每月例行重启一次 | 境外解析占比极低，重启期间有降级与告警兜底。可用性真的变重要时再做 |
| 查询日志按来源 IP 筛选 | — | 违背「不记录客户端 IP」的隐私设计。不做 |
| 黑名单、访问控制加备注字段 | 生产上两份清单都是空的 | 没有使用场景。不做 |

## 测试与守卫怎么留

- **保留**测「两边是否对得上」的契约测试：前端调用的接口后端有没有、开发 mock 与后端字段、危险操作有没有确认说明。它们对应过真实事故，也不限制具体写法。
- **不写**钉死某种写法、某句文案的文本扫描测试。换一种同样正确的写法就误报的测试，是负担不是保护。
- 新守卫写完要把缺陷种回去，确认它真会报警。这个项目里多次出现「测试是绿的，但不是因为它测的那件事」。
